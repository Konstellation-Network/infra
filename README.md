# infra

Terraform + Ansible for the Konstellation validator fleet and supporting
infrastructure. Private, permanently (`ENGINEERING.md §6.4`) — this is a map
of where the validators live.

Structure follows `ENGINEERING.md §6.4`:

```
terraform/
├── modules/
│   ├── hetzner/{validator,sentry,rpc,archive}/   # hcloud
│   └── gcp/{validator,sentry,rpc,archive}/        # google
└── envs/testnet-1/                                 # instantiates both providers for one network
ansible/
├── roles/{node,cosmovisor,horcrux,monitoring,firewall}/
├── inventories/testnet-1/                      # generated by terraform, see below
├── site.yml                                    # full fleet config, idempotent
├── upgrade.yml                                 # stages a checksummed binary via cosmovisor
└── requirements.yml                            # ansible-galaxy collections (community.general, ansible.posix)
monitoring/
├── prometheus/alerts.yml                       # missed blocks / peers / block-time / disk / no-new-blocks
└── grafana/                                    # empty — see grafana/README.md
```

`runbooks/` doesn't exist yet — writing a halt/upgrade/key-rotation/incident
runbook before there's a fleet to rehearse it on would be fiction. Add it once
testnet-1 is standing and the first halt drill (`ENGINEERING.md §13`, §15
Phase 5) happens.

## Status

Scaffolding only. **No `terraform apply` or `ansible-playbook` run has
happened against real infrastructure** — there's no Hetzner project, no GCP
project, no release binary to install, and no key ceremony yet. Everything
below is what exists in code, not what's running.

Verified so far (no cloud credentials needed for any of this): `tofu fmt
-check`, `tofu validate` on every module and on `envs/testnet-1` (OpenTofu —
a drop-in, terraform-compatible CLI; `terraform` itself works identically),
`ansible-playbook --syntax-check` on `site.yml`/`upgrade.yml`, and
`ansible-lint` clean except the intentional `var-naming` trade-off documented
in `ansible/.ansible-lint`. Not verified: an actual `plan`/`apply` (needs a
real Hetzner token and GCP project) or anything ansible actually touching a
live host.

## Current scope: testnet-1 only, split across Hetzner and GCP

Started on Hetzner alone; GCP was added on request to run both. There's no
interconnect between the two clouds in this scaffold, so the topology is
deliberately two self-contained halves rather than one fleet spanning a
shared private network:

| | Hetzner | GCP |
|---|---|---|
| Validators | 3 (`v1`-`v3`), no public IP | 2 (`v4`-`v5`), no public IP |
| Sentries | 3, 1:1 with their validator, public | 2, 1:1 with their validator, public |
| Archive | 1, internal only | 1, internal only |
| RPC | — | 1, public |

Each validator's sentry lives in the **same cloud**, on that cloud's own
private network — that pairing can't cross clouds without a VPN/interconnect
neither side has. Sentries from both clouds peer with each other (and any
other testnet-1 node) over the public internet exactly like normal p2p, so
the fleet still functions as one network; only the validator↔own-sentry link
needs to be private. `terraform/envs/testnet-1/hetzner.tf` and `gcp.tf` each
own their half's network, firewalls, and module calls.

This goes further than `ENGINEERING.md §9.4`'s "5, all in-house" strictly
requires — it's closer to the provider/ASN diversity that's actually a
mainnet concern (D7) — but doesn't violate it: all keys are still team-held.
`terraform/envs/konstellation-1/` doesn't exist yet; don't assume this
2-cloud split is the final mainnet topology without revisiting §9.2/D7 then.

**GCP validators use Local SSD, and that choice needs to be read, not just
trusted:** `terraform/modules/gcp/validator`'s `local_ssd_count` variable has
the full explanation, but the short version — GCP Local SSD doesn't survive
a stop or most host maintenance events (only a plain reboot), and a VM with
Local SSD attached can't live-migrate, so maintenance always means a stop.
Losing that disk loses `priv_validator_state.json`, and a validator that
restarts and re-signs without it is the double-sign scenario `ENGINEERING.md
§2.7` calls unrecoverable (5% slash, no undo). This was chosen anyway for
testnet-1 to match Hetzner's local-NVMe performance profile on the other
half of the fleet. `ansible/roles/node` stripes the Local SSDs into one RAID0
array (a single 375 GiB disk doesn't meet the multi-TB spec either way) but
does nothing to mitigate the durability risk — **re-decide this before any
mainnet validator runs on GCP**, probably in favor of `pd-ssd` despite its
worse commit latency, or a documented backup path for
`priv_validator_state.json` specifically.

## Known gaps — not yet built

- **Bastion host.** Validators and archive nodes have no public IP, so SSH
  needs a jump host on each cloud's private network. Not yet a terraform
  module; `var.bastion_ipv4` in `envs/testnet-1` is a placeholder for
  whatever fills this role (it can be one host reachable from both clouds,
  or one per cloud — not decided).
- **Monitoring host.** `monitoring/prometheus/alerts.yml` and the
  `prometheus.yml.example` scrape config assume a central Prometheus/Grafana
  box that can reach both clouds' private networks. No terraform module
  provisions it yet.
- **Dedicated horcrux cosigners.** `ansible/roles/horcrux` currently co-locates
  the cosigner with the validator host — a simplification. `ENGINEERING.md
  §9.2` calls for 3+ cosigners spread across separate hosts/regions (and, per
  the point above, probably separate clouds now). Revisit before real
  validator keys exist.
- **GCP validator disk durability** — see the callout above. Not a gap so
  much as a decision deliberately deferred past testnet-1.
- **Version pins are empty.** `konstellationd_version`, `konstellationd_sha256`,
  `cosmovisor_sha256`, `horcrux_sha256`, `node_exporter_sha256` are blank in
  `group_vars`/role defaults on purpose — `konstellation` hasn't cut a release
  build yet (Phase 2, in progress per the org `STATUS.md`). Every download task
  in these roles asserts its checksum var is non-empty and fails closed rather
  than skip verification.
- **Terraform state backend** (`terraform/envs/testnet-1/backend.tf`) is a
  partial `gcs` config with no bucket chosen yet.
- **Metric names in `alerts.yml`** are CometBFT's documented convention, not
  yet confirmed against a live `/metrics` endpoint (see the caveat comment
  in that file).
- **IPv6** is only opened on the Hetzner sentry/RPC firewalls, not GCP's
  (would need a dual-stack VPC there) — a minor asymmetry, not a security gap.

## Apply flow (once the gaps above are closed)

```bash
cd terraform/envs/testnet-1
cp terraform.tfvars.example terraform.tfvars   # fill in, do not commit
gcloud auth application-default login           # or set GOOGLE_APPLICATION_CREDENTIALS
terraform init -backend-config=backend.hcl      # backend.hcl gitignored, not yet written
terraform plan
terraform apply
# writes ansible/inventories/testnet-1/hosts.yml from outputs

cd ../../../ansible
ansible-galaxy collection install -r requirements.yml
ansible-playbook site.yml --limit validators --check   # dry run one group first
ansible-playbook site.yml
```

Fleet upgrades: `ansible-playbook -i inventories/testnet-1 upgrade.yml -e upgrade_name=... -e binary_sha256=... -e binary_url=...` (`ENGINEERING.md §16`). One invocation covers both clouds — `upgrade.yml` targets `hosts: all`.
